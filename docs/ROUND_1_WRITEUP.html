2. Starting Point

The extension was constructed from scratch using the official VS Code Extension API (v1.120+) and TypeScript, directly consuming the @truefoundry/trueforge-sdk. We engineered custom modules for inline diff decorations, non-destructive virtual hunk staging, and token-bounded context assembly rather than adopting bulky external loop engines, ensuring strict compliance with competition harness boundaries.

3. Architecture on TrueForge

The extension acts as a native VS Code client communicating with the local TrueForge agent harness over HTTP/SSE:

  • Turn Lifecycle: Turns are dispatched via client.sessions.createTurnStream. Tokens and tool calls stream through Server-Sent Events, rendering directly without blocking the editor UI thread.
  • Editor MCP Tools: Four workspace primitives are exposed to TrueForge: read_file (range-bounded file reader), search_workspace (regex and pattern scanner), propose_file_edit (stages modifications into in-memory hunks requiring user consent), and run_terminal_command (test and command execution).
  • Tool Approval Driving Diff Review: TrueForge tool proposals trigger virtual diff hunks. Files remain untouched on disk until the developer explicitly clicks "Accept Hunk" or "Accept All".
  • Context Engineering & Compaction: Agent definitions configure dynamic context compaction thresholds (16k tokens) and subagent delegation for structured task planning.

4. How Context is Selected

A custom Context Assembly Engine manages repository information under a strict 32 KB (approx. 8,000 tokens) budget:

  • Explicit Mentions: The prompt parser identifies @file:<path> and @symbol:<name> tags, guaranteeing priority placement in the context payload.
  • Autonomous Relevance Discovery: When no files are specified (e.g. Task B), the engine tokenizes task instructions, removes stop-words, and scores workspace files via structural and semantic heuristics (CLI entry points, test suites, documentation files).
  • Budget Partitioning: 20% system directives/MCP schemas, 55% retrieved source chunks, 15% conversation history, and 10% safety margin. Files are ranked by score and packed greedily until the 32 KB threshold is reached.
  • Audit Transparency: In Task B, the engine visibly displays the selected files, their sizes, and the exact rationale in the sidebar before code generation begins.

5. Model Setup

  • Primary Model: Local Ollama qwen2.5-coder:7b served via TrueForge's OpenAI-compatible provider at http://localhost:11434/v1.
  • Secondary Fallback Model: Configured backup endpoint on local Ollama, ensuring automatic failover during Task C.
  • Operational Cost: $0.00 — runs fully on local workstation compute.
  • Switching Mechanism: Configurable via VS Code settings (trueforge.serverUrl) or handled automatically by the client's internal failover handler.

8. Known Limitations & 30-Day Roadmap

  • Limitations:
    1. Context ranking currently relies on keyword frequency and path heuristics rather than a live Language Server Protocol (LSP) call-graph.
    2. Multi-turn diff resolution handles unified line hunks cleanly, but AST-aware syntactic block transformations would improve resilience against overlapping edits.
  • Future Roadmap:
    1. LSP Indexing: Integrate VS Code semantic symbol providers (vscode.executeDocumentSymbolProvider) for AST-level context pruning.
    2. Multi-Agent Verification: Introduce a background reviewer subagent that automatically runs pytest in a sandboxed worktree before prompting the developer.
